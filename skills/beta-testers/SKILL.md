# Beta testers

Spawn a panel of realistic, app-specific human personas who actually click through the live UI and report every broken flow, layout failure, and moment of confusion in a structured format a developer can immediately reproduce and fix.

Read [`../../docs/harness.md`](../../docs/harness.md) when mapping subagent or browser calls to your active runtime.

## Hard rules

1. **Drive the real UI, never fake it from source code.** A finding counts only if a tester observed it in a live browser, rendered view, or project verification harness. If no safe live UI can run, stop and report the exact blocker.
2. **Never touch real customer data or paid side effects.** Use local dev, isolated/demo mode, or a user-approved staging environment with outbound mail/SMS/billing neutralized. Never run destructive actions against production.
3. **Personas must fit this app.** Read the product context before casting personas. Do not reuse generic filler names or generic missions unrelated to what the app actually does.
4. **Every bug must be reproducible.** Drop vague complaints ("felt clunky") unless tied to an exact screen, element, step sequence, and observed failure.

## Workflow

Open a checklist with these five phases before spawning anything:
1. Context & target setup
2. Cast 10 personas
3. Parallel live testing
4. Verify & deduplicate
5. Developer-ready report

---

### Phase 1: Context & target setup

1. **Understand the product and scope:**
   - Read `README.md`, `PRODUCT.md`, `DESIGN.md` (if present), primary routes/pages, and UI copy/locales.
   - If the user points to a PR, branch, or feature area, inspect `git diff <base>...HEAD` to identify every changed screen and adjacent flow.
   - Write down a 3-line **App Brief**: what the product does, who uses it, and the 2-4 primary journeys to test.
2. **Resolve the live UI runner (in priority order):**
   - **Project verification skill** (preferred): check `.agents/skills/verify-*/`, `.cursor/skills/verify-*/`, or `.claude/skills/verify-*/` (for example, one generated by [`/create-ui-verification-skill`](../create-ui-verification-skill/SKILL.md)). Launch it in its safest non-destructive mode (`--mode demo` or `--mode isolated`) and verify `doctor` passes.
   - **Running local or staging URL** given by the user, or start the repo's documented dev server on an ephemeral port with safe/stubbed external keys.
   - **Browser driver**: use headless Playwright/Chromium, the project's `verify-*` CLI, or the runtime's browser subagent. Each tester must run in its **own isolated browser context** (separate cookies, storage, viewport, color scheme) so sessions never collide.
3. **Define the safe boundary:** record the exact base URL, test account/login method (if any), and actions that are off-limits (for example: live payment submit, deleting shared seed data).

---

### Phase 2: Cast 10 personas

Read [`references/persona-archetypes.md`](./references/persona-archetypes.md) and cast **10 distinct personas** (or `N` if the user asks for a smaller/larger panel; never fewer than 5 for a full pass).

Each persona combines:
- A **domain-authentic identity** grounded in this app's real users (role, age, goal, why they opened the app today).
- One of the **10 behavioral/device archetypes** from [`references/persona-archetypes.md`](./references/persona-archetypes.md) so the panel always covers low-tech hesitation, mobile-first thumbs, desktop keyboard speed, double-clicking/impatience, messy input, zoom/accessibility, dark mode/theme switching, slow/interrupted flows, zero-context first-timers, and tech-savvy edge poking.
- If the app supports multiple locales, pull the locale rules from [`../locale-craft/SKILL.md`](../locale-craft/SKILL.md) and assign at least 2 personas to switch to non-default locales (especially the longest-string language) to catch clipped buttons, raw keys, and awkward phrasing.
- A concrete **starting URL, viewport, color scheme, and 2-3 step mission**.

Present the 1-line roster table in your working notes (not a wall of text) before fanning out.

---

### Phase 3: Parallel live testing

Spawn the persona subagents in parallel (all 10 at once when the host has headroom, or two waves of 5 if local browser memory is tight — never starve the user's machine).

Every persona subagent receives a standalone brief containing:
1. The **App Brief**, base URL, safe boundary, and how to invoke the browser/verification tool (with an isolated session/context).
2. Their exact **Persona Card** (identity, viewport, theme, behavior traits, mission).
3. The strict **Return Schema** from [`references/report-schema.md`](./references/report-schema.md).
4. These rules:
   - Stay in character while testing, but write your final report like a crisp QA engineer.
   - Exercise real user interactions (click, tap, type, submit, Back, reload, resize). Never call internal dev setters.
   - Capture console errors, uncaught page errors, failed network responses (`4xx`/`5xx`), horizontal overflow, clipped controls, broken focus, and screenshots for every failure.
   - Report **0 bugs** if nothing breaks; never invent issues to look thorough.
   - Separate **Functional / Layout Bugs** from **UX Friction** (worked technically, but stalled or misled this persona).

---

### Phase 4: Verify & deduplicate

When all personas return:

1. **Drop unverified claims.** Any report missing repro steps, URL, or observed evidence goes into a "Dropped (insufficient evidence)" count, not the main list.
2. **Merge duplicates by root symptom.** When multiple personas hit the same bug (for example, submit button double-fires or overlaps on 390px mobile), combine them into one item and record `Hit by: k/10 personas (...)`.
3. **Spot-check every P0/P1 bug.** Re-verify every blocker or major bug once (or confirm directly from its captured screenshot + console/HTTP evidence) and map it to the likely route/component file in the codebase so the developer can jump straight to the fix.
4. **Tear down cleanly.** Stop any local dev server or headless browser processes started for the run, while preserving captured screenshots/artifacts in the named evidence directory.

---

### Phase 5: Developer-ready report

Output ONE consolidated report using the exact structure in [`references/report-schema.md`](./references/report-schema.md):

1. **Run Summary**: target URL/mode, commit SHA, personas completed (`N/10`), evidence folder path, and counts by severity.
2. **Functional & Layout Bugs (P0 -> P3)**: each with stable ID (`BT-01`, `BT-02`), severity, `Hit by`, likely source file/route, exact repro steps, expected vs actual, viewport/theme, console/network errors, and screenshot path.
3. **High-Signal UX Friction**: ranked by how many personas stalled or misread the UI, with exact screen/copy and a concrete fix idea.
4. **Persona Coverage Table**: one row per persona (`Persona`, `Device/Theme`, `Mission`, `Outcome`, `Bugs Found`).
5. **Recommended Fix Order**: top 3-5 items to fix first, with suggested regression checks.
